# Job Application Tracker — Design Document

A 3-tier web application for tracking job applications. Built in staged layers,
each adding exactly one new piece of real-world complexity.

**Repo:** `job-application-tracker`
**Stack:** FastAPI (Tier 2) + PostgreSQL (Tier 3) + vanilla HTML/CSS/JS (Tier 1)

---

## 1. Architecture

Three tiers, each with one job, talking only to their neighbours.

```
Browser  ──HTTP+JSON──►  FastAPI  ──SQL──►  PostgreSQL
(Tier 1)              (Tier 2)            (Tier 3)
Presentation          Application          Data
```

Hard rules:

- The browser never talks to the database. It only talks to the API.
- JSON is the browser↔API language. SQL is the API↔database language.
- Tier 2 is the translator between those two languages, and the only place
  business rules live.

---

## 2. Data model

One table: `applications`.

| Column        | Type         | Notes                                         |
|---------------|--------------|-----------------------------------------------|
| `id`          | integer (PK) | Auto-generated by the database                |
| `company`     | text         | Required, non-empty                           |
| `role`        | text         | Required, non-empty                           |
| `status`      | text         | One of: applied, interviewing, offer, rejected|
| `applied_date`| date         | Required, cannot be in the future             |
| `created_at`  | timestamp    | Set by the database on insert                 |
| `updated_at`  | timestamp    | Set by the database, refreshed on every update|

`status` is constrained to a fixed set of values — that constraint is enforced
in Tier 2 (validation) and ideally also in Tier 3 (a CHECK constraint or enum)
as defence in depth.

## 3. API contract

Base path: `/applications`

| Method | Path                  | Purpose                  | Request body        | Success response       |
|--------|-----------------------|--------------------------|---------------------|------------------------|
| GET    | `/applications`       | List all applications    | —                   | 200, JSON array        |
| GET    | `/applications/{id}`  | Get one application      | —                   | 200, JSON object       |
| POST   | `/applications`       | Create an application    | JSON (no id)        | 201, the created record|
| PATCH  | `/applications/{id}`  | Update fields            | JSON (partial)      | 200, the updated record|
| DELETE | `/applications/{id}`  | Delete an application    | —                   | 204, no body           |

Error cases the API must handle:

- 404 when `{id}` does not exist (GET one, PATCH, DELETE).
- 422 when the body fails validation (bad status value, empty company,
  future applied_date). FastAPI + Pydantic give most of this for free.

## 5. Build stages

The whole point: each stage adds **one** new hard thing. Do not start the next
stage until the current one fully works end to end.

### Stage 1 — In-memory
Data lives in a Python structure in `store.py`. No database. Goal: get Tier 1
and Tier 2 talking — all five endpoints working, the frontend able to add, list,
edit, and delete. Restarting the server wipes all data; that is expected here.

### Stage 2 — PostgreSQL
Replace the in-memory store with a real database via SQLAlchemy. Data now
survives restarts. Introduces connection handling, the `applications` table,
and the JSON↔SQL translation in earnest.

### Stage 3 — Docker
Each tier in its own container, wired together with Docker Compose. The API
container and the database container talk over a Docker network. This is the
DevOps payoff — start from fundamentals, no copy-pasting.

### Stage 4 — nginx
A reverse proxy in front: serves the static frontend and routes `/api` calls to
the FastAPI container. Production-shaped layout.

## 6. Teaching contract

Carried over from previous projects:

- Predict before running — state what you expect to happen first.
- Paste full terminal output and full response bodies — show, don't summarise.
- Type solutions by hand — no copy-paste of code you don't understand.
- Collaborative debugging — we read the actual error together.
- `.gitignore` first, before the first commit. Secrets never committed.
